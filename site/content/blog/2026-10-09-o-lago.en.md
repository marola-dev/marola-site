# The Lake

2026-10-09

tags: adr

marola will keep its data in a data lake: Parquet files, an open format, in a bucket (a folder on a cloud storage service), with a catalog next to them and no server running. that will let the map show the last report it kept when an agency goes offline, and stops the beaches' history from being lost. this post explains why a lake, and not a database or a data warehouse, suits what marola wants to be. it is this blog's first architecture decision record (ADR), and the post that [Sic Mundus Creatus Est](news.html#sic-mundus-creatus-est-en) promised.

## the context

eight times a day, every map update fetches the state agencies' bathing-water reports from scratch and throws away what it fetched. the OpenStreetMap beach lists survive only in a temporary cache in GitHub Actions, the automation that builds the map. when an agency goes offline, the map loses its reports: on October 1 the site's health check found no sampling points in any area, according to MIP-0075, the Marola Improvement Proposal that designs the lake ([§2](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md#2-motivation)). and nothing keeps the history.

the history exists. IMA (Instituto do Meio Ambiente), Santa Catarina's environmental agency, publishes every sample taken at every beach since 2003, with wind, tide, rain, water and air temperature, the bacteria count and the verdict ([MIP-0056, §2](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0056-oods-open-ocean-data-store.md#2-motivation)). that is about 190,000 samples in Santa Catarina alone ([MIP-0075, §4.3](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md)). Rio and Bahia come next; in all, 14 states monitor their beaches ([§2](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md#2-motivation)).

## the decision

we keep everything in a [DuckLake](https://ducklake.select/): the tables are Parquet files, an open columnar format, and a DuckDB catalog records every table, every file and every version ([MIP-0075, §4.4](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md#44-the-table-format-ducklake)). weekly jobs, running marola-app's code from marola-oods, will write to the lake, and the map's build will read its exports instead of calling the sources on every update. a database comes in only when something needs to answer each request on the spot, and then as its own proposal ([§11](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md#11-open-questions)).

## why a lake

- **storage is cheap.** by the MIP's estimate, Santa Catarina's whole history should fit in a few megabytes (MB) of Parquet, and 14 states, with 30 days of versions kept, stay well under 100 MB ([MIP-0075, §4.3](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md)). that fits easily inside a storage service's free tier.
- **it is easy to move.** the lake is files in an open format that any program compatible with S3 (Simple Storage Service, the file-storage standard Amazon created) can read. it was designed for Backblaze B2, and the proposal [marola#692](https://github.com/marola-dev/marola/pull/692) now moves it to Cloudflare R2; both are cloud file-storage services. the move changes the address and the key, not the design.
- **it is hard to maintain.** DuckLake lacks the rules a database uses to reject duplicate or invalid rows (primary key, unique and CHECK, a rule that tests each value); it only has NOT NULL, which forbids empty fields. the job that writes and a file of checks keep the data in order ([marola-oods#22](https://github.com/marola-dev/marola-oods/pull/22)). and because the catalog is one file each job downloads and uploads back, only one job can write at a time, or one erases the other's work ([MIP-0075](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md), "Risk"). that is the price, and the project accepts it. in the words of marola's maintainer: "I've got the maintenance covered."
- **machine learning needs history, from many sources.** knowing whether a point tends to turn unfit after rain, or how the water changes from one season to the next ([MIP-0056](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0056-oods-open-ocean-data-store.md)), takes years of reports next to years of weather and sea data. a model reads that all at once, in bulk. our bet is that columnar files serve it well and a database built to answer one request at a time does not: the MIP itself rules such a database out for the history ([MIP-0075, §9](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md#9-alternatives-considered)). marola's machine learning lives in [marola-ml](https://github.com/marola-dev/marola-ml), away from the map.

## a cheap analogy

the lake is where machine-learning engineers like to swim: anything fits, in many formats, with all the history, and a bit of mess comes with it. the data warehouse is the pool: more structured, less chaotic, good for the BI crowd (business intelligence: business reports and dashboards), who want the same questions answered the same way every month. and the oceans? only the oceanmen can answer that one.

## the consequences

- the map will survive an agency being offline: it shows the last report it kept, with its date, until the 45-day rule retires it ([MIP-0075, §3](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md#3-user-visible-change)).
- loading the same data twice changes nothing, and the versions of the last 30 days let us roll back.
- no server runs between loads, and there is no database to pay for.
- the rules a database would give for free become checks written and tested on their own.

## where it stands

[MIP-0075](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0075-water-quality-store-r2.md) is still a draft. the lake's structure ([marola-oods#22](https://github.com/marola-dev/marola-oods/pull/22)) and the move to R2 ([marola#692](https://github.com/marola-dev/marola/pull/692)) are in review. the first write to the bucket still waits on an exception to the project's phase rule (marola works one phase at a time, and a cloud service belongs to Phase 2), not yet granted. the lake has not received any data yet. beaches go in first, then Santa Catarina's water quality, then Rio's and Bahia's.
